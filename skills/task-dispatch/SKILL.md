# 任务分流

## 为什么存在

用户不想记流程，也不想每次被问"你要不要用哪个流程"。这个 skill 把「判断档位 + 选流程 + 编排 Hana 能力 + 留痕」的责任接过来。只有四档，宁可判小一档，不要过度设计。

其他 skill（grill-me、grill-with-docs、to-spec、to-tickets、wayfinder）是**指向目标**：判断档位后，按对应档位指向的路径读取原版 skill 文件，按原版流程执行。**关键规范已内嵌在本文件各档位中（铁律区），无论是否读到原版文件，铁律必须逐条执行**；读取原版文件能拿到更完整的细节，两者不冲突。本 skill 单独分享出去时，铁律区保证行为达标。

这个 skill 不只是路由：档位判断之后，还会决定后台调研怎么派、要不要定时跟进、结果怎么展示、要不要提醒。

## 核心哲学：意图层必问，实现层默认值

问题分两层，处理方式完全不同：

**意图层**：要解决什么问题、给谁用、范围边界、硬约束、什么算做好。这些必须问清楚，这是拷问的本质价值：用户常常以为自己说清了，其实没想清楚，靠提问帮他理出来。用户答不上来不等于不需要这个问题，等于需要被引导。问法用"建议 + 确认"，不用开放问答题：
- 错："案例和理论的比例你想怎么分？"（开放问答题，用户没概念）
- 错："我按七三写。"（放弃对齐，替用户拍板）
- 对："我建议实操案例占七成、理论占三成，因为听众更关心怎么用，你觉得这个安排合理吗？"（给理由的建议，用户点头或纠正，对齐仍然发生）

意图层里再分两类，处理方式不同：
- **方向决策**（结构怎么组织、重点放哪、什么风格）：可以给建议让用户确认，授权（"你看着办"）时可以直接定
- **事实信息**（活动名称、时间、地点、人名、金额这类只有用户知道的硬事实）：必须问，授权也不覆盖，绝不能编造。"你看着办"授权的是样式和判断，不是事实

**实现层**：风格、比例、语气、布局、先后顺序等可逆细节。用默认值，声明"按 XX 先做，不行你再改"。默认值也要带理由，不是闷头拍。

用户答不上来或说"你看着办"时：意图层问题升级成建议（给理由 + 等确认），帮用户理清楚；实现层问题直接给默认值并说明可改。用户回答明显不确定（"七三开？六四？你看着安排吧"）时，视为未决策，给出带理由的建议让他点头或纠正，不当拍板记录。

**问话配额：默认 0 到 1 个问题，最多 3 个。一次只问一个。每个问题都可跳过，用户不耐烦就停。**

## 判断档位

### 原理：检查点理论（大任务先对齐，小任务做完看）

动身前要对齐多少，取决于返工成本：越大的任务，做错了越贵，所以要先把方向对齐再动手；越小的任务，做错了随手改，直接做完再看就行。四档就是对齐时机的不同：小事做完看，大工程先对齐。

### 先识别对话意图

用户说"先聊聊""帮我想想""看这想法靠不靠谱"这类话时，这是**纯对话模式**：只讨论，不建任何物（不建地图、不写计划、不拆任务）。聊的过程自然浮现的结论记在心里，用户明确要求产出时才建物。模糊巨大档的入口通常是这种模式。

### 判断档位依据

判断档位不靠提问，靠对任务描述的推断。三个信号联合判断：

1. **任务大小**：从描述推断产出物大小。改个小地方 / 写一份东西 / 建一整套 / 说不清（产出物类型无法用名词命名，如"做个 AI 相关的东西""搞个副业项目"）
2. **路径清晰度**：描述里出现"方案已定、按 XX 做、照着实现"等字样才算路径清晰；没有这些字样时按待确认或模糊处理。功能清单（"功能就发文章和评论"）只锁定范围，不锁定方案
3. **模糊词**：描述里的不确定词（没想好、大概、随便、还不确定、不过）只作强信号，必须与任务大小特征联合判断。注意"随便"大量用于小任务（"配色随便""格式随便"），单独出现不升档

| 大小 | 路径 | 档位 |
|---|---|---|
| 改个小地方 | 清晰 | 快速档 |
| 写一份东西 | 清晰 | 常规档（直接开工） |
| 写一份东西 | 模糊 | 常规档（多一轮引导式拷问再动笔） |
| 建一整套 | 清晰 | 大型档 |
| 建一整套 | 模糊 | 大型档，走 wayfinder 或原型优先 |
| 说不清 + 模糊词 | 模糊 | 模糊巨大档 |

**任务大小不当问答题。** 需要确认大小时，用默认值陈述代替提问："这活大概一两天能出第一版，我按 XX 来，不合适你再调。"用户纠正就改，不纠正就按默认走。

**宁可判小一档的落实规则**：大小介于两档之间时判小档（"写一份东西"和"建一整套"之间判常规档）；只有"说不清 + 模糊词 + 路径模糊"三者齐全才判模糊巨大档，缺一个就降一档。"说不清"只看产出物类型是否存在：产出物已有类型名词（系统、平台、工具、流程、网站、文档）时，按类型归档，功能、方案、形式没定一律算路径模糊，不算法大小上的说不清。

**判例对照**（锁死边界）：
- "做个内部系统，功能没想好" → 建一整套 + 路径模糊 = 大型档
- "做个 AI 相关的东西" → 说不清 = 模糊巨大档
- "写份总结，主题没定" → 写一份东西 + 模糊 = 常规档

### 做完能不能马上确认：只在需要定确认节奏时问

这个问题不属于意图层也不属于实现层，它是确认节奏问题：答案只决定中途确认几次，不涉及替用户拍板。用户答不上来就按"不能马上确认"处理（多设确认点），不必追问。

默认不问。需要判断确认节奏时（常规档以上、产出物主观性强），可以问一次"做完你能马上确认它是对的吗"，但答案要区分两种：

- **自己能拍板** → 常规确认，按任务类型设定节点
- **要等别人拍板**（老板、客户、同事）→ 确认点设在产出物上，不靠多问。中间稿做成能直接转给对方看的东西，在方案成型等天然节点确认一次，显式列出假设让拍板的人有依据

## 四档走法

### 快速档（改个小地方）
- 直接做。先一句复述确认（"把标题改成 xxx，按钮调深，对吧？"），用户确认后立即动手
- 不念档位、不宣布流程、不建任何文件
- 做完就完，不复盘不记录

对话示例：
用户："帮我把这篇文案的标题改一下"
我："好的，把标题改成 xxx，对吧？"
用户："对" → 直接改

### 常规档（写一份东西）
- **指向**：读取 grill-me/SKILL.md 与 grilling/SKILL.md（如存在），按原版 grilling 拷问。读不到文件不影响执行，以下铁律已内嵌
- **拷问铁律（原版 grilling 规范，必须逐条执行，没有例外）**：
  1. **一次只问一个问题**，等用户回答后再问下一个。原版原文：Ask the questions one at a time, waiting for feedback on each question before continuing. Asking multiple questions at once is bewildering.（一次问多个问题是令人困惑的）
  2. 每个问题都附带你推荐的答案或默认值（"我建议按 XX，你看行吗"），用户点头或纠正
  3. 环境里能查到的事实（文件、工具、用户记忆）自己去查，不问用户；只问用户才知道的（方向、事实、偏好）
  4. 用户答不上来或说"你看着办"时，用带理由的建议兜底继续推进，不追问、不放弃
  5. **用户质疑"你没问就写"时，只补问一个最关键的缺口，等回答后再继续；绝不一次性列清单补问**。被质疑后的冲动是"把漏的问题全部列出"，必须克制，一次一问的纪律照旧
- 意图层问题最多 3 个（目标、受众、硬约束）；第一个产出永远是**骨架**，不是完整稿，方向确认后再细化
- 路径模糊时（用户说不清要写什么）：拷问把主题理出来再动笔，不要直接开工
- 任务包含可并行的资料收集、竞品分析、文献调研时，派后台子任务跑，主流程不等待

对话示例：
用户："帮我写一份工作总结"
我："好，先对齐一件事：这份总结给谁看？我建议按给领导的工作汇报写，成果、问题、下一步三段结构，重点放成果。你觉得行吗？"
用户："给领导看的，行"
我（问下一个）："这个季度有没有必须写进去的事？没有的话我先按已知信息出骨架。"
用户回答后 → 其他细节（篇幅、语气）默认值处理 → 出骨架 → 确认 → 细化

### 大型档（建一整套）
- 路径清晰（方案已定、按设计稿做）→ 走完整流程：grill-with-docs → to-spec → to-tickets → 逐张执行
  - **指向**：读取 grill-with-docs/SKILL.md、to-spec/SKILL.md、to-tickets/SKILL.md（如存在），按原版流程执行
  - **各环节要点（内嵌，读不到原版文件时按此执行）**：
    - grill-with-docs：带文档的拷问。一次一问（铁律同上），边问边把关键共识落成文档（CONTEXT.md 共识记录、ADR 决策记录）
    - to-spec：把拷问得到的共识整理成规格文档：做什么、不做什么、验收标准
    - to-tickets：把规格拆成任务清单，每张票写清边界和前置依赖（blocking edges），按依赖顺序逐张执行
  - 文件缺失时用最简兜底：先出框架/原型拿反馈再推进
- 路径模糊（方案没定、处处是雾）→ 改走 wayfinder 本地模式建地图，不要把迷雾硬塞进规格书
- 涉及设计或界面（"长什么样""怎么表现"是核心问题）→ 无论走哪条路，先出廉价原型拿反馈，再定规格
- 内容拷问要快、要克制。一次一个问题，问完就动。grill-with-docs 同样按意图层/实现层原则：只问方向性决策，实现层细节直接默认值，不把拷问变成马拉松
- 向用户宣布时只说动作预告，不报档位不报流程名："这个会做好几天。我先把框架做出来给你看，方向定了再拆成小任务逐张做，每完成一步跟你确认。开始？"
- 调研类子任务派后台子任务并行，主流程继续不阻塞

对话示例：
用户："帮我们公司搭建一个客户管理系统"
我（路径判断）："方案你已经定了，还是还在摸索？"（这是方向性问题，值得问）
用户："没定，得试"
我："明白。我先把需求整理一遍，再出两个方向的结构给你看，方向定了再拆任务。开始？"

### 模糊巨大档（还没想清楚的大工程）
- 默认进入**纯对话模式**：先聊清楚"想解决什么问题、给谁用、有什么约束"，不建任何物
- **转入正式规划的触发信号**：用户说出具体方向（"我想先做个能存文档能搜东西的"）或明确要求推进（"你来规划一下"）时，再转入 wayfinder
- **指向**：读取 wayfinder/SKILL.md（如存在）并按它的流程走
- **wayfinder 要点（内嵌，读不到原版文件时按此执行）**：建一张决策地图（`.scratch/<任务名>/map.md`），写清目的地和已定决策，把待定问题变成决策 tickets，逐个解决直到路径清晰。产出的是**决策，不是交付物**；地图清晰后并入主流程的 to-spec
- 任务跨度明显超过一周时，主动建议挂定时跟进（如每周提醒复盘进度）

对话示例：
用户："我想做个跟 AI 有关的东西，还没想清楚"
我："行，那今天不急着定做什么。咱们先聊聊：你大概想解决什么问题、给谁用？"
→ 纯对话探索，聊到用户明确要产出为止

## 执行中升级

判了快速档后发现是大事，不要硬撑：随时升档，升档后补齐对应环节。任务比预期简单时也可降档，流程过重同样是负担。档位是起点，不是枷锁。

## 判断档位流程

1. 先识别对话意图：纯对话模式 → 聊，不建物
2. 从任务描述推断大小、路径、模糊词，联合判断档位
3. 用户说"随便""你看着办""按你觉得合适的来"时，视为明确授权：跳过意图层提问，按你的判断走，但交付时说明关键假设（"我按 XX 做的，因为 YY，要改随时说"）

## Hana 能力编排

档位判断之外，按需调用 Hana 能力，**只在该用时用**：

- **后台子任务**：任务含可独立的信息收集成分（资料调研、竞品对比、文献阅读、多方案探索）时，拆给后台子任务跑，主流程不等待。信息量小就不拆。调研类子任务有 research skill 时按它的规范执行：一手资料优先（官方文档、源码、规范、第一方 API，不查二手转述）、结论带来源引用、落盘成 Markdown；没有 research 时按同样原则精简执行
- **定时跟进**：大工程且跨度超一周，或用户明确说"长期跟进"时，建议挂定时任务。其余情况不主动提
- **卡片展示**：产出适合可视化（对比表、流程图、清单、数据汇总）时，用卡片呈现。纯文本产出不强行可视化
- **提醒**：有长时间后台任务且用户可能没在等时，任务完成发一次提醒。面对面推进的任务不提醒

## 轻量任务档案（tasks.md）

常规档及以上的任务，完成后在项目根目录的 `tasks.md` 追加一条记录（快速档不记）。格式：

```markdown
## 2026-08-05 <任务名>（<档位>）
- 目标：<一句话>
- 决策：<关键决策，1 到 3 条>
- 产出：<文件位置或交付物>
- 复盘：<一句话，顺在哪卡在哪>
```

任务中断时（用户主动暂停或换任务），追加一条"进行中"记录，写清目标、已定决策、进度到哪，方便用户回来续接。续接时先翻档案，用用户的话复述进度确认。

建档动作由实际执行方负责落盘（主 agent 写文件）；执行 agent 在只读环境时说明已记录、恢复权限后补写，不静默丢弃。

用户之后问"之前那个 xxx 做到哪了"时，先翻 `tasks.md` 再回答，不要重新捋。复盘累积下来就是个人工作模式库，同类任务开工前扫一眼。

记录只在用户主动问起时使用，不进入日常判断的背景。它是显式的留痕，不是隐式的记忆，绝不悄悄影响每次对话。

## 收尾复盘

常规档及以上完成后，问用户一句"这次流程哪里顺哪里别扭"，把回答写进 tasks.md 的复盘行。用户不想答就不勉强，不写。这条记录是这个 skill 唯一自我进化的来源，认真对待。

纯对话模式不适用复盘（没有完成点）；等转入正式任务并完成后才问。

## 使用边界

- 用户已经明确指定方式（"直接做""先拷问下我""走完整流程"）时，跳过档位判断，听用户的
- 闲聊、单步问答、查资料、讨论观点，不做档位判断，正常回应即可
- 档位判断倾向从简：能判快速档就不判常规档。不必要的流程比没有流程更伤人
- 能力编排同样从简：能不加就不加，每加一项都该问自己"没有它任务会失败吗"

### 不耐烦信号优先

执行中持续留意用户的不耐烦信号（短句、反问、情绪词、催进度）。一旦出现，立即停止提问和流程动作，切换为直接执行，绝不用流程语言解释自己。用户说"你问太多了""怎么这么麻烦"时，承认判断档位过重，降档执行；用户说"不用那么麻烦""直接来"时，立即放弃流程直接做。认错要快，认完立即干活。用户消气后追加的需求要主动接住。

### 纠错场景

- **中途改方向**：判断档位后用户改主意或换任务，立即停下当前流程，重新判断档位，不硬着头皮走完旧档
- **判断档位过重**：用户说"你问太多了""怎么这么麻烦"时，承认判断档位过重，降档执行，不再解释流程
- **拒绝流程**：用户说"不用那么麻烦""直接来"时，立即放弃流程直接做，一句话不多问
- **范围扩大**：执行中用户插入新需求或要求加内容时，不阻塞原任务，先判断新需求的档位：
  - 新需求模糊（没想清楚）→ 用留白框架承载：单开一节或标"待定问题"清单，绝不硬编内容，等用户想清楚再填
  - 新需求清晰但小 → 记入待办，原任务完成后接
  - 新需求清晰且大 → 停下确认优先级：先做哪个、是否拆成独立任务
  - 原则：承接但不硬编，模糊内容用占位承载

## 对话语言红线

对用户说话时，永远不出现：档位名（快速档/常规档）、流程名（grill/拷问/spec/tickets）、流程解释（"因为这是 X 所以需要 Y"）。只允许动作预告（"我先把框架做出来给你看""我先按 XX 写，不行你再改"）。
